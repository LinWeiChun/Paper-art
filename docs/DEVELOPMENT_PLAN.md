# PaperArt 開發流程與驗收規劃

整理日期：2026-10-07。

依使用者提供的「網站App開發流程規劃」與現有專案文件整理，將一般 SDLC 套用至既有 PaperArt。
本文件是後續執行基準；未完成的需求、設計、測試及 UAT 不因列入規劃而視為完成。
現況見 [CURRENT_STATUS.md](CURRENT_STATUS.md)，工作清單見 [TODO.md](TODO.md)，部署見 [DEPLOYMENT.md](DEPLOYMENT.md)。

## 產品目標與範圍

- 既有定位：剪紙藝術作品展示平台。
- 本輪方向：穩定作品瀏覽與管理流程，建立可追溯的需求、測試、驗收及發布紀錄。
- 規劃角色：訪客與管理者；實際需求、角色權限及驗收者需於第一階段確認。
- 維持 React、Spring Boot、MySQL 與 Cloudflare R2 既有架構，優先重用元件、Service、Repository 與 API。
- 本輪不包含原生 App、新增商業功能或框架更換；如有需求，另定範圍。
- 目標使用者、成功指標與時程尚待確認，不直接套用通用專案的月份估算。

## 十二個階段

| 階段 | 工作 | 產出與完成條件 |
|---|---|---|
| 1. 產品目標 | 確認使用者、問題與產品價值 | 記錄目標、成功指標及範圍 |
| 2. 需求分析 | 整理功能、權限、效能、安全與例外情境 | User Story 與可操作的驗收條件 |
| 3. 版本範圍 | 區分本輪必做、後續及排除項目 | 有優先級與相依關係的版本清單 |
| 4. UX 流程 | 整理瀏覽、搜尋、詳情、返回與後台管理 | 正常、失敗、空資料及權限不足流程 |
| 5. UI 規範 | 盤點既有元件與行動版行為 | 共用元件、Loading、Error、Empty State 規則 |
| 6. 技術設計 | 核對 API、資料關聯、安全與部署 | API 契約、資料變更及必要設計紀錄 |
| 7. 工程基礎 | 核對開發環境、CI、分支及秘密管理 | 可重現的執行方式與隔離測試安排 |
| 8. 開發 | 依確認需求修改既有程式 | 實作、必要測試、審查與文件完成 |
| 9. QA | 執行 API、整合、回歸與相容性測試 | 含版本與環境的案例結果及缺陷清單 |
| 10. UAT | 由指定人員操作業務流程 | 驗收者、日期、結果與未解問題 |
| 11. 發布 | 核對設定、備份、回復及授權後部署 | 發布版本、部署紀錄與發布後檢查 |
| 12. 維運 | 觀察錯誤、效能、資源及回饋 | 告警、事件紀錄、還原演練及下一輪待辦 |

PaperArt 已有功能與部署歷史，先補齊缺口，再對每次變更執行適用階段，不重建整個專案。

## 執行順序

1. 核對現況與版本範圍：釐清部署、功能狀態、API 契約與驗收條件。
2. 核心穩定性：重現並修復搜尋 500、有效作品載入失敗及必要操作狀態。
3. 篩選與體驗：核對 Tag、Featured、Rentable、Sort、URL 同步與行動版。
4. 安全與資料維運：查核 Access、Rate Limit、ruleset，再規劃 Flyway、備份、回收站及 R2 生命週期。
5. 驗收與發布：每次發布依所含範圍完成 QA、UAT、備份、回復方案與發布後檢查。

步驟 4 中若發現實際安全或資料風險，應提前；不必等所有未來功能完成才發布已驗收的修正。

## 需求紀錄格式

每個工作項目記錄：編號、使用角色、目的、前置條件、操作流程、驗收條件、排除範圍、
API／資料影響、優先級、相依項目、負責人與驗收者。

搜尋需求範例（待確認）：身為訪客，希望透過關鍵字及篩選找到作品，且分享 URL 後可還原相同條件。
驗收時須先確認搜尋欄位、比對方式、空白與特殊字元處理、排序及分頁規則；不得由實作自行推定產品需求。

## 核心驗收案例

| 編號 | 情境 | 預期結果 | 本輪結果 |
|---|---|---|---|
| QA-01 | 空條件、有效關鍵字與無結果搜尋 | 依 API 契約回應；無結果有明確提示 | 未執行 |
| QA-02 | 不合法搜尋參數及邊界輸入 | 依契約驗證；可預期輸入錯誤不產生非預期 500 | 未執行 |
| QA-03 | 有效作品及不存在的作品詳情 | 有效作品正常顯示；不存在作品回傳約定 404 並提示 | 未執行 |
| QA-04 | Filter／Sort 個別及組合操作 | UI、URL、API 請求及結果符合確認規格 | 未執行 |
| QA-05 | 清除、重新整理、上一頁及分享 URL | 還原預期條件，列表與詳情切換狀態一致 | 未執行 |
| QA-06 | 登入、登出、未登入與權限不足 | Cookie、CSRF、CORS 與權限判斷符合既有安全設計 | 未執行 |
| QA-07 | 登入失敗達限制及解除限制 | 依設定限制登入，無非預期繞過或永久鎖定 | 未執行 |
| QA-08 | 作者／分類／Tag／作品管理 | 驗證、儲存、失敗提示與權限正確；前台反映預期結果 | 未執行 |
| QA-09 | 圖片上傳成功與失敗 | 回應清楚，資料庫與 R2 關聯符合規格 | 未執行 |
| QA-10 | Excel 匯入正常及錯誤資料 | 依確認規格處理資料與錯誤，不留下非預期部分結果 | 未執行 |
| QA-11 | Loading、網路失敗及空資料 | 不誤顯舊結果；可重試或返回 | 未執行 |
| QA-12 | 選定瀏覽器與手機尺寸操作 | 列表、Drawer、詳情及後台主要流程可完成 | 未執行 |

此表為案例概要；執行前補上輸入資料、步驟、明確預期值與環境。
每次結果須附提交版本、日期、執行者、證據及缺陷連結；歷史成功樣本不得覆蓋本輪未執行狀態。
涉及寫入的測試使用隔離資料與儲存空間。

## 三個關卡

| 關卡 | 必要條件 |
|---|---|
| 需求確認 | 範圍、正常及例外流程、權限與驗收條件明確 |
| 開發完成 | 實作與文件更新、Code Review、必要單元及整合測試通過 |
| 發布就緒 | QA、回歸及 UAT 完成；重大缺陷處理；備份與回復方案就緒 |

阻斷主要流程、越權或資料毀損的缺陷必須先處理；其他缺陷記錄影響、後續處理與驗收決定。
既有 CI 涵蓋前端 lint/build 與後端 formatting/test，不能視為完整前端行為、MySQL、R2 或跨網域登入驗證。

## 隔離驗證與環境選擇

| 安排 | 優點 | 限制 |
|---|---|---|
| 本機隔離環境與 CI | 可先完成核心修正，無須重建雲端 staging | 無法完整代表雲端路由、網域、Cookie 與服務整合 |
| 經確認後重建 staging | 可驗證實際部署與跨服務流程 | 有費用及維護成本，須重新建立資料與設定 |

維持 staging 暫停；先完成本機及 CI 可驗證工作。涉及雲端的必要情境若未驗證，列為發布缺口，
由負責人決定隔離驗證安排；不能將未測標為通過，也不自動重建環境。
具體發布步驟以 [DEPLOYMENT.md](DEPLOYMENT.md) 為操作基準。

## 責任與排程

- 產品負責人／驗收者：確認目標、範圍、優先級與 UAT 結果。
- 開發者：完成設計、實作、必要測試及文件。
- 發布負責人：核對環境、備份、回復、部署與監控。

同一人可兼任，仍需分別保留結果。問題重現與待辦盤點完成後再估算工時、相依關係及里程碑日期。
詳細規格或測試紀錄增加時，先確認既有文件可否承載，再拆分並更新 README 導覽。
